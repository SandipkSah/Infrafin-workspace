db1 /data: GitLab Container Registry Storage Report

As of 2026-10-02 · Sandip Sah

Summary

The GitLab container registry uses 1.5 TB of the 6.4 TB used on db1 /data, and almost all of it is old image
tags that nothing ever deletes. 71 repositories hold 4,651 tags. Registry garbage collection works correctly,
but it only removes images that are no longer tagged, and no tag cleanup is running.

- Fix: enable GitLab cleanup policies on the image-building projects. The data/ group alone holds about 1.4
  TB.
- Expected effect: a “keep the newest 10 tags” rule removes about 4,100 of 4,651 tags (89%). Each tag carries
  0.5–0.9 GB of unique layers, so we expect roughly 1 TB or more to be freed. Space returns 24–48 h after the
  tags are deleted.
- No manual GC is needed, and it isn’t safe: the registry runs on the metadata database, where the old offline
  registry-garbage-collect would delete live images.

Proposed cleanup policies

Cleanup policies are set per project: Project → Settings → Packages and registries → Container registry →
Cleanup policies. This needs the Maintainer role. For many projects at once, use the API (PUT /projects/:id
with container_expiration_policy_attributes).

Phase 1: remove old release candidates (low risk)

RCs are superseded by their release, and nobody should be deploying them to production.

  Setting                  Value
  ------------------------ -----------------------------
  Enabled                  yes
  Run cleanup              every day
  Keep the most recent     5 tags
  Keep tags matching       main|prod|stable|release-.*
  Remove tags older than   7 days
  Remove tags matching     .*rc\d+

Phase 2: general retention (after the team agrees)

  Setting                  Value
  ------------------------ -------------------------------------------------------------------
  Enabled                  yes
  Run cleanup              every day
  Keep the most recent     10 tags per image name
  Keep tags matching       main|prod|stable|release-.* plus any version pinned in production
  Remove tags older than   90 days
  Remove tags matching     .*

Notes:

- The 90-day rule and the import date: all tags imported on 2026-07-11 count as created that day, so a 90-day
  rule first deletes them on 2026-10-09. After that the policy runs normally. For faster relief, pick 14 or 30
  days instead.
- A deleted RC frees no space if its release is a retag of the same image. In that case the layers stay
  referenced by the release. Phase 1 may free less than expected, and Phase 2 frees the rest.
- For immediate relief, the bulk tag-delete API applies the same rules right away, per registry repository
  (once per hour per repository):
  DELETE /projects/:id/registry/repositories/:repo_id/tags?name_regex_delete=...&keep_n=...&older_than=...

How to set up a cleanup policy in the GitLab UI

Repeat these steps for each image project. Start with a pilot: trading/mktdataapi has 155 tags but only 2.8
GB, so a mistake there costs little. Then do the large data/ projects.

Before you start

  -------------------------------------------------------------------------------------------------------------
  Check                                                  Why
  ------------------------------------------------------ ------------------------------------------------------
  You have the Maintainer (or Owner) role on the project Only Maintainers can edit cleanup policies

  The team has agreed on the keep-rules                  Deleted tags can’t be restored

  You know which tags production pulls from this project Those tags must match “Keep tags matching”, or be
                                                         among the newest 10
  -------------------------------------------------------------------------------------------------------------

Steps

1.  Open the project in GitLab, e.g. data/snp_analyst_etl.
2.  In the left sidebar, go to Settings → Packages and registries.
3.  In the Cleanup policies section, click Edit cleanup rules (shown as Set cleanup rules if the project has
    never had a policy).
4.  Turn on Enable cleanup policy.
5.  Run cleanup: select Every day.
6.  Under Keep these tags:
    1.  Keep the most recent: select 10 tags per image name.
    2.  Keep tags matching: enter main|prod|stable|release-.*, plus any production versions, e.g.
        main|prod|stable|release-.*|2026\.08\.4.
7.  Under Remove these tags:
    1.  Remove tags older than: select 90 days (or 14/30 days for faster relief, see Notes above).
    2.  Remove tags matching: enter .*.
8.  Click Save changes. The page now shows Next cleanup scheduled to run on …. Note that date.
9.  After the first run, check the result:
    1.  Deploy → Container registry in the project: the tag count per image should have dropped to about 10
        plus the kept tags.
    2.  On db1: docker exec gitlab-ee gitlab-ctl registry-database gc-stats. The review queues fill, then
        drain as GC removes the data.
    3.  On db1, 24–48 h later: df -h /data shows the space coming back.

Regex rules for the two pattern fields

  Rule                                                Correct            Wrong
  --------------------------------------------------- ------------------ ------------------------------------
  Separate alternatives with |, no commas or spaces   main|prod|stable   main, prod, stable
  “Anything” is .*, not *                             release-.*         release-*
  Don’t type the anchors; the page adds \A and \z     .*rc\d+            \A.*rc\d+\z
  The pattern must match the whole tag name           .*rc\d+            rc\d+
  A literal dot needs a backslash                     2026\.08\.4        2026.08.4 (also matches 2026x08y4)

The tag latest is always kept, so it doesn’t need to be in the keep pattern.

How the rules combine

A tag is deleted only if it matches “Remove tags matching”, does not match “Keep tags matching”, is not among
the newest 10 of the candidates for its image, and is older than the chosen age. If any keep rule applies, the
tag stays.

Changing or stopping a policy

  Goal             Action
  ---------------- -------------------------------------------------------------------------------------
  Pause cleanup    Turn off Enable cleanup policy and click Save changes. Future runs stop
  Change a rule    Edit the field and save. Any saved change reschedules the next run
  Undo deletions   Not possible: deleted tags can’t be restored, so the image would have to be rebuilt

Rollout plan

1.  Confirm the open checks below, especially which tags production runs.
2.  Agree on the keep-rules with the image owners (data/ETL, trading, dashboards).
3.  Phase 1 (RC cleanup): try it on one small repository first, then roll out to all projects via the API.
4.  Phase 2 (keep newest 10): roll out to the projects with 50+ tags (29 repositories).
5.  Watch reclamation for 48 h with gitlab-ctl registry-database gc-stats and df -h /data.
6.  Follow-up: fix Dockerfile layer caching so each build stops adding 0.5–0.9 GB.

Open checks before deleting

- ☐ Existing cleanup policies: are any already enabled? (ContainerExpirationPolicy.where(enabled: true) in
  gitlab-rails runner)
- ☐ Deployed tags: on every host that runs these images, list them with
  docker ps --format '{{.Image}}' | grep <registry-host>, and check compose and CI deploy files for pinned
  versions. Deleting a tag doesn’t stop a running container, but a restart or redeploy that needs to pull it
  will fail.
- ☐ RCs retagged as releases: compare tags.manifest_id in the registry DB to estimate how much Phase 1 really
  frees.
- ☐ Pin the GitLab image: if /srv/docker/gitlab-ee compose uses gitlab/gitlab-ce:latest, pin it to 19.4.0-ce.0
  before anyone recreates the container. Otherwise it upgrades silently and runs registry DB migrations.
- ☐ Cleanup worker capacity: check Admin → Settings → CI/CD → Container Registry. Defaults may need several
  daily runs to work through 4,651 tags.
