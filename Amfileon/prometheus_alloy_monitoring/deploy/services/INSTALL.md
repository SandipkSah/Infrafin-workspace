# ClickHouse, Redis and GitLab metrics

Dashboards **ClickHouse**, **Redis** and **GitLab** (`grafana-local/`, generated by `gen_dashboards.py`)
and six alert rules (`db1/prometheus/alert.rules`, group `services`) are ready. Their container
CPU/memory panels (cAdvisor) and the gitlab.amf HTTPS check already show data; everything else
needs the steps below. Which instances are collected: [`../alloy/service-targets.txt`](../alloy/service-targets.txt)
(production + staging; dev, the plain `clickhouse` projects and app-internal Redis are out of scope).

| Service | Change to the service | Who | Effect on the service |
|---|---|---|---|
| Redis (12) | **none** — Alloy's built-in exporter logs in on the published port | you: 1 script per host | none (a few INFO commands every 30 s) |
| ClickHouse (14 containers on db1/db2/prod3) | one `<prometheus>` block added to the config file already mounted | owner / you: 1 script per container | **servers: none** (picked up without restart); keepers: restart only if wanted (`--restart`) |
| GitLab (gitlab-ee, db1) | 11 lines appended to `/etc/gitlab/gitlab.rb` | owner / you | `gitlab-ctl reconfigure`: Puma/Sidekiq restart, a few seconds of 502s |

**Security:** no new port is published on any host. ClickHouse `:9363` and GitLab's metrics ports
listen only inside their containers; Alloy reaches them by joining their Docker networks
(`docker-compose.override.yaml`, generated): `clickhouse-*_default` and, for GitLab, `proxy_network`
(gitlab-ee's only network — so other containers on proxy_network can read GitLab's counters too).
Redis passwords live only in `/srv/docker/alloy/redis.env` (root, 600), written on the host and
never printed or copied off it. Metrics are counters only — no table, key, repository or user data.

`discover.sh` output is reflected in `service-targets.txt` (networks). Findings:

## 2. ClickHouse — owner's service, one container at a time

```bash
for h in db1 db2 prod3; do scp deploy/services/enable-clickhouse-metrics.sh $h: ; done
ssh -t db1 'bash ~/enable-clickhouse-metrics.sh db1.staging.ch.amf'
```
Per run: backs up the mounted config file to `/root/clickhouse-config-backups/`, adds the block,
checks the XML, then waits for the port.

- **Servers (8): no restart.** ClickHouse re-reads its config files while running and opens :9363
  within seconds — running queries, inserts and merges continue (tested 2026-10-28 with 26.3: a
  90-second query kept running, uptime kept counting, port open after 4 s).
- **Keepers (8): optional.** They don't open the port on reload. Without `--restart` the script
  only puts the block in place (the port opens at their next restart, whenever that happens);
  with `--restart` it restarts that keeper. Only the Keeper table on the dashboard needs them.

Keeper restarts, if wanted — one at a time; production has 3 keepers (quorum holds), staging has 2
(staging's replicated tables are read-only for a few seconds while one restarts).

## 3. GitLab — owner's service

Appending to `gitlab.rb` + `reconfigure` takes seconds. Putting the lines into
`GITLAB_OMNIBUS_CONFIG` instead would need `docker compose up -d`, i.e. recreating the container:
minutes of downtime, and with `image: gitlab/gitlab-ce:latest` it would also start any newer
`latest` that has been pulled meanwhile — an unplanned upgrade. Move the lines into the compose file
at the next planned GitLab update.

```bash
scp deploy/services/gitlab/gitlab.rb.snippet db1:
ssh -t db1
  sudo docker exec gitlab-ee cp -p /etc/gitlab/gitlab.rb /etc/gitlab/gitlab.rb.bak-amf-monitoring
  sudo docker exec -i gitlab-ee tee -a /etc/gitlab/gitlab.rb >/dev/null < ~/gitlab.rb.snippet
  sudo docker exec gitlab-ee gitlab-ctl reconfigure
  for p in 8083/metrics 9229/metrics 8082/metrics 9168/sidekiq; do sudo docker exec gitlab-ee curl -s -o /dev/null -w "$p %{http_code}\n" http://localhost:$p; done
```
All four should print `200`. Rollback: `sudo docker exec gitlab-ee cp -p /etc/gitlab/gitlab.rb.bak-amf-monitoring /etc/gitlab/gitlab.rb && sudo docker exec gitlab-ee gitlab-ctl reconfigure`.
